# Claude через MCP

Підписка Claude (claude.ai, застосунок, Claude Code) підключається до сервісу
як **Custom connector** і отримує руки: читати памʼять про людей, пошту,
задачі, цілі — і зберігати готовий результат.

## Головний принцип

Через Anthropic API кожен токен коштує грошей і крутиться на нашому сервері.
MCP перевертає схему: **думає той Claude, за якого вже сплачено підпискою,
наш застосунок лише дає інструменти.** Тому:

- `crm_get_owner_voice` віддає, як пише власник;
- `crm_get_contact_memory` віддає все, що система памʼятає про людину;
- `crm_save_message_draft` / `crm_save_email_draft` зберігають текст **дослівно**;
- жоден інструмент не запускає нашу генерацію — витрати на модель від MCP = 0.

Це не скасовує фонові джоби (коуч о 16:00, розбір пошти, консолідація памʼяті):
там немає людини в чаті, і вони далі йдуть через API-ключ. MCP покриває
інтерактивну частину — коли ти сам у Claude просиш «напиши Марії».

## Підключення (один раз)

1. **Integrations → Claude (MCP) → Створити адресу.** Отримаєш
   `https://<домен>/mcp/<64 hex>`.
2. **claude.ai → Settings → Connectors → Add custom connector** → встав адресу.
   Поля під токен там немає — він уже в адресі.
3. **Claude Code:** `claude mcp add --transport http networking <адреса>`.

Адреса = пароль. Показується лише в кабінеті, не публікується. Витекла —
**Перевипустити**: стара помирає одразу. **Відключити** — прибирає зовсім.

Перевірка: у чаті Claude спитай «кому мені пора написати?». У панелі зʼявиться
«Claude звертався: …» (оновлюється не частіше разу на 5 хв).

## Транспорт

Streamable HTTP, stateless JSON, без сесій.

| | |
|---|---|
| `POST /mcp/<token>` | JSON-RPC 2.0; відповідь `application/json`; нотифікація → **202** з порожнім тілом |
| `POST /mcp` | те саме, токен у `Authorization: Bearer`, `X-Networking-Token` або `?token=` |
| `GET` | 405 + `Allow: POST, DELETE, OPTIONS` — потік сервер→клієнт не потрібен |
| `DELETE` | 204 |
| `OPTIONS` | 204 + CORS `*` (автентифікація не кукою, тож CORS нічого не захищає; без нього не працює MCP Inspector) |

SSE віддається лише коли клієнт **не приймає** JSON (`Accept: text/event-stream`
без `application/json`). Простий JSON надійніший за напіввідкриті потоки крізь
nginx.

Методи: `initialize`, `ping`, `tools/list`, `tools/call`. Решта — `-32601`.
Версії протоколу: `2025-06-18`, `2025-03-26`, `2024-11-05`; ехо клієнтської,
якщо знаємо, інакше найновіша.

**Помилка інструмента — всередині результату з `isError: true`**, не помилка
протоколу: Claude бачить причину і виправляється сам, а клієнт не рве
зʼєднання. Помилки протоколу — лише для битих повідомлень.

## Безпека

- токен: 32 байти з `secrets.token_hex`; **формат перевіряється регуляркою до
  запиту в БД** — порожнє чи сміттєве значення інакше могло б зматчитись із
  чужим ключем;
- порівняння сталого часу (`secrets.compare_digest`);
- `/mcp` поза сесійною авторизацією: клієнт — сервер Claude, у формі конектора
  Basic чи PIN ввести ніде;
- рейт-ліміт 240 запитів/хв на IP; `Cache-Control: no-store`;
- застосунок однокористувацький, тож ізоляції «токен = акаунт» як окремого
  кейсу немає: токен один, дані одні.

Токен лежить у `integration_tokens` під `provider="mcp"` — та сама таблиця,
що й Google, без нової схеми.

## Профілі для фонового воркера

`/mcp/<token>?profile=reply|inbox|memory|social|coach|sync` обмежує `tools/list`
до 4–8 інструментів однієї фонової задачі (менше схем у контексті — менше
квоти). Без профілю — інтерактивний набір із 22 інструментів нижче; 19
фонових (`crm_get_pending_reply`, `crm_fill_reply_draft`, `crm_triage_email`,
`crm_save_dossier`, `crm_set_coach_question`, синк задач…) у ньому не
показуються, але викликаються. Деталі — [BACKGROUND_AI.md](BACKGROUND_AI.md).

### Профіль `sync` — чек-лист Claude

Запланована задача Claude, що синкає картки «Задач Олега» із задачами
сервера, підключається з `?profile=sync` і бачить шість інструментів:

| Інструмент | Відповідь (JSON рядком) |
|---|---|
| `crm_upsert_task` — створити/оновити за (`source`, `external_id`), без дублів | `{"uid", "created", "status"}`, за потреби `"conflict": "done_on_server"` |
| `crm_list_task_changes` — створене, змінене, закрите, видалене після `since` | `{"server_time", "changes": [...]}` |
| `crm_link_task` — звʼязати рідну задачу з карткою | `{"uid", "linked"}` |
| `crm_close_missing` — закрити те, чого джерело більше не має | `{"closed": [...], "count"}` |
| `crm_complete_task`, `crm_send_owner_message` | текст, як і в інших профілях |

На відміну від решти інструментів, ці відповідають JSON, а не прозою: їх
читає програма. Контракт і діагностика — [CLAUDE_CHECKLIST.md](CLAUDE_CHECKLIST.md).
Кожен виклик пишеться в панель «Синк з чек-листом» на сайті (час, інструмент,
остання помилка).

## Інструменти (22 інтерактивних)

| Читання | Дії |
|---|---|
| `crm_get_owner_voice` — стиль і правила | `crm_save_message_draft` — дослівно в Telegram з кнопкою «Надіслати» |
| `crm_get_contact_memory` — досьє, факти, історія, дописи | `crm_save_email_draft` — дослівно, і в чернетки Gmail |
| `crm_search_contacts` — по імені/компанії, далі семантично | `crm_send_email_draft` — **незворотно**, позначено destructive |
| `crm_list_due_contacts` — кому пора, з приводом | `crm_log_interaction`, `crm_add_fact` |
| `crm_list_inbox`, `crm_get_email` | `crm_create_task`, `crm_complete_task` |
| `crm_list_tasks`, `crm_list_goals`, `crm_list_gates` | `crm_log_goal_progress`, `crm_create_gate`, `crm_close_gate` |
| | `crm_create_idea`, `crm_save_link`, `crm_set_reminder` |

Вивід — компактний текст із короткими id (`#12`, `#a1b2c3`), не сирий JSON.
Контакт приймається як `#id` або частина імені; кілька збігів — інструмент
просить `#id`, а не вгадує. Аргументи нормалізуються (ліміти клампляться,
дати — `YYYY-MM-DD`), помилки дієві: «у контакту немає Telegram, є email —
`crm_save_email_draft`».

`instructions` у відповіді `initialize` задають порядок: голос → памʼять →
написати самому → зберегти дослівно → зафіксувати взаємодію. Без цього модель
іде найзнайомішим шляхом.

## Тести

`tests/test_mcp.py`: юніти на чисті функції (версії, гард токена, JSON/SSE,
конверти, статична валідація всіх схем, нормалізація аргументів) і наскрізний
прогін живим клієнтом: handshake, 202 на нотифікацію, `tools/list`, реальні
виклики на даних, і негативи — чужий/короткий/відсутній токен → 401, GET →
405, SSE-клієнт, Bearer/заголовок/query, перевипуск убиває стару адресу,
падіння інструмента не рве транспорт.

## Якщо з claude.ai не підключається

Бойове підключення з UI конектора — перше. Дивитись у логи контейнера: 401 —
адреса не та (перевипусти й встав заново), 405 — клієнт стукає GET-ом, що
нормально для розвідки, далі має піти POST. Заголовок `Accept` у логах
покаже, чи клієнт просить SSE.
